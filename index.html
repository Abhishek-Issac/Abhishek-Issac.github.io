/01 · about

A small introduction.

I’m a self-taught developer from a hill town in Kerala. Most of what I’ve learned came from broken file-share bots, late-night flashing sessions, and a stubborn need to understand why something didn’t work the first time.

I’m Abhishek Issac — sixteen, based in Wayanad, Kerala in southern India. I work mostly in Python using Pyrogram for Telegram, with Motor on top of MongoDB and asyncpg on top of PostgreSQL when a project needs to keep its data around.

Almost all of my code was first written on a phone — a Poco X3 Pro running Termux. That constraint shaped how I think: prefer plain text, keep dependencies small, avoid anything that needs more than 6 GB of RAM to run, and assume the network might drop mid-deploy. Every project here is built with that mindset.

When I’m not pushing commits I’m usually flashing a custom ROM on the same Poco X3 Pro (currently a OxygenOS 15 port for vayu/bhima, before that crDroid, HyperOS ports, and the original MIUI), recovering a friend’s bricked OnePlus over fastboot, or cramming chapters of +1 BioScience — Botany, Zoology, Physics, Chemistry, Maths, English and Hindi.

I keep this site small on purpose. No frameworks, no build step, no tracking — just hand-written HTML, CSS and a single JavaScript file that talks to the GitHub API and animates the things you’re scrolling past.

/10 · how I work

Build small. Ship fast. Refactor in public.

I’d rather have a working version one in production tonight than a beautiful diagram on Monday. The commit graph is my notebook — features land in tiny pieces, and refactors happen out in the open instead of in a long-lived branch.

Two things get optimized first: uptime for the people using the bot, and readability for whoever has to debug this at 2 AM on a phone keyboard — usually a slightly-tired version of me. Everything else is negotiable.

I keep dependencies small, prefer plain text, and write code that I’d be okay reading on a 6 GB phone over a flaky connection. That covers most of what I’ll ever need this site to do, too.

/11 · principles

Three rules I keep coming back to.

Not testimonials. Just three short sentences I’ve said out loud often enough that they’ve become a working philosophy.

“Ship the smallest version that helps a real person, then iterate from feedback — not from a whiteboard.”

/01 — on shipping

“If a script can run on a 6 GB phone over 4G, it can probably run anywhere I’d ever deploy it. Optimize for the worst environment first.”

/02 — on constraints

“The future-me reading this code at 2 AM has zero patience for cleverness. Plain functions, named variables, boring patterns.”

/03 — on readability
